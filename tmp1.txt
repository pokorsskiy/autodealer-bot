CLAUDE.md
This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Project overview
A console tool for finding arbitrage opportunities on CS2 skins via the DMarket API. It shows the order book (TARGET = buy orders, OFFER = sell offers), spread, and renders it with ANSI colors.

Рабочий регламент (workflow)
These rules govern HOW work is done in this repo and OVERRIDE default behavior. The user writes in Russian; reply in Russian.

Жёсткие правила (всегда)
IMPORTANT: НИКОГДА не делай git commit/git push/PR без явного «да» от пользователя, данного прямо перед командой. «Сделай коммит» в составе большой задачи — НЕ авторизация. Всегда показывай финальный git diff/статус и спрашивай подтверждение непосредственно перед коммитом.
YOU MUST сначала согласовать план нетривиальной задачи (см. Этап 1) и приступать только после явного «да».
YOU MUST делать минимальные изменения — не рефакторить несвязанный код.
Один логический коммит = одно изменение. Не собирать всё в один гигантский коммит.
Если есть два подхода — опиши оба и дай пользователю решить (используй вопрос-выбор).
НИКОГДА не коммить секреты, .env, токены, ключи, maFile, *.xlsx.
Стоп-фразы (завершать ими сообщение, когда нужно участие пользователя)
⏸️ Запрашиваю разрешение на коммит — всё готово, нужен «да» на git commit.
⏸️ Требую согласования — нужно утвердить план/решение перед началом.
⏸️ Жду утверждения — работа приостановлена до ответа.
⏸️ Ожидаю утверждение коммита — синоним финального стопа перед коммитом.
После любой из этих фраз НЕ продолжай работу и НЕ коммить до явного ответа пользователя.

Перед любой нетривиальной задачей: изучи контекст → выпиши план → заверши фразой ⏸️ Требую согласования и остановись. Приступай только после явного утверждения. Формат:

## План: <название задачи>

### Цель
- что нужно получить

### Шаги
1. ...

### Затрагиваемые файлы
- `path/to/file` — что и зачем

### Краевые случаи / риски
- ...

### Открытые вопросы
- ... (или «нет»)

⏸️ Требую согласования
Этап 2: команда /закрепить (подготовка к коммиту)
Когда пользователь пишет «закрепить» (или /закрепить), выполни строго по порядку и НЕ коммить до ответа:

Перепроверка кода — перечитай весь git diff; прогони линтер/типы/тесты, если есть; проверь на TODO, отладочные print, закомментированный мусор, секреты; убедись, что изменения соответствуют согласованному плану и ничего лишнего не затронуто.
Обновление памяти — запиши в auto-memory / MEMORY.md всё, что стоит сохранить между сессиями (новые команды, архитектурные решения, подводные камни, исправленные ошибки).
Обновление CLAUDE.md — отрази новые правила, команды, конвенции, изменения архитектуры.
Обновление README.md — обнови, если изменилось поведение, появились фичи, команды, зависимости, конфиги.
Обновление tmp/TODO.md — сверься со списком дел: перенеси выполненные пункты в раздел ✅ (с датой и кратким итогом), сними/закрой то, что стало неактуальным, заведи новые задачи, всплывшие по ходу работы. Держи статусы (🔴/🟡/🟢/⚪/✅) актуальными.
Отчёт + запрос — сформируй отчёт (формат ниже), предложи текст коммита (conventional commits: feat:/fix:/refactor:/…), заверши фразой ⏸️ Запрашиваю разрешение на коммит и остановись. Коммить только после явного «да».
Формат отчёта:

## Отчёт: <название задачи>

### Что сделано
- ...

### Изменённые файлы

- [x] отладочный код убран
- [x] секреты отсутствуют
- [x] соответствует согласованному плану

### Обновлено

- CLAUDE.md: <что или «без изменений»>
- README.md: <что или «без изменений»>
- tmp/TODO.md: <что или «без изменений»>

### Предлагаемый коммит
`<тип>: краткое описание`

### Требует внимания / открытые вопросы
- <... или «нет»>

⏸️ Запрашиваю разрешение на коммит
Команда /автономно — АВТОНОМНЫЙ режим
Когда пользователь пишет /автономно (или «работай автономно»), переходи в автономный режим для крупной задачи (полное ревью / рефактор / обновление под новый API / оптимизация / разбиение монолита). В этом режиме правила меняются так:

Что разрешено без переспроса

Принимать все обратимые технические решения самостоятельно (структура модулей, имена, порядок рефактора, какой мёртвый код удалить, какие эндпоинты обновить по openapi.json) — не останавливайся на ⏸️ Требую согласования для них.
Делать коммиты по ходу (один логический коммит = одно изменение), НО: предупреждение про секреты остаётся жёстким — секреты/.env/ключи/maFile/*.xlsx не коммить НИКОГДА.
Что НЕ разрешено даже автономно (стоп и запись вопроса)

Необратимое/внешнее: git push, PR, удаление данных не под git, изменение зависимостей с потенциальным ломанием, любые реальные торговые/деньговые вызовы к живому DMarket/Buff API. Такие моменты — записать вопрос и продолжить с остальным.
Неоднозначность бизнес-логики: если непонятно, КАК должна себя вести фича с точки зрения пользователя (а не как её технически сделать) — записать вопрос, выбрать разумный дефолт, пометить его и идти дальше.
Как вести вопросы и проблемы

По ходу автономной работы всё, что требует внимания оператора, копи в ДВА места:

Кратко — в чат (в конце ответа): нумерованный список «Вопросы/Проблемы» — 1–2 строки на пункт.
Подробно — в файл отчёт-N.md (в корне проекта; N — следующий свободный номер, начиная с 1; файл gitignored через отчёт-*.md). Формат каждого пункта:
## [N.M] <краткий заголовок>
- **Тип:** вопрос к оператору / проблема / принятое решение (дефолт)
- **Где:** `path/to/file:line` — функция/участок
- **Суть:** что именно неясно или что сломано
- **Контекст:** почему это встретилось, что зависит от ответа
- **Варианты:** если применимо — вариант A (плюсы/минусы), вариант B (…)
- **Мой дефолт:** что я выбрал/сделал, пока нет ответа (если применимо)
- **Статус:** открыт / решён
Файл отчёт-N.md начинай с шапки:

# Автономный отчёт N
- **Дата:** <YYYY-MM-DD>
- **Задача:** <что делалось>
- **Итог:** <что сделано, коммиты, что осталось>

## Вопросы к оператору
...

## Проблемы
...

## Принятые решения (дефолты)
...
Финал автономной сессии

В конце: краткий отчёт в чат (что сделано, ссылка на отчёт-N.md, список открытых вопросов) + путь к файлу отчёта. НЕ пушить. Ждать оператора для необратимого.

Команда /отчёт о проблеме (генерация отчёта в tmp/)
Когда пользователь просит зафиксировать проблему: создай файл tmp/отчёт-<краткое-описание>-<YYYY-MM-DD>.md (slug в kebab-case), создай tmp/ при отсутствии, НЕ коммить его (убедись, что tmp/ в .gitignore), заполни по формату и сообщи путь. Формат:

# Отчёт о проблеме: <название>

- **Дата:** <YYYY-MM-DD>
- **Серьёзность:** критическая / высокая / средняя / низкая
- **Статус:** обнаружена / в работе / решена

## Суть проблемы

Стоп-условия (жди подтверждения перед)
